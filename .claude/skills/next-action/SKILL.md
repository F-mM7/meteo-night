# MeteoNight AI 強化：次アクション策定

AI 強化セッションの起点。**現状把握 →（meteo / tstar）→ タスク整理 → 次アクション策定**を行い、ユーザーに着手候補を提示するところまでが責務。

> **方針: 策定であって着手ではない。** このスキルの成果物は「今から着手すべき 1 タスクの提案＋根拠」。実装・ベンチ・採用判定は行わない（それは evolve-meteo-ai-handwritten スキル、または tstar 依存タスクの受け取り作業の仕事）。提案はユーザーの裁定を待つ——`CLAUDE.md` のとおり、議論段階で勝手に作業を始めない。**根拠は必ず `ai/OBJECTIVE.md` の物差し序列（L1 厳密性 / L2 self-play 不動点 / L3 家族外挑戦）に紐付ける**。「強くなりそう」だけで候補を選ばない。

## このスキルが答える 4 つの問い

1. **meteo の AI はいま何が配信され、どこが天井か**（`ai/` 台帳）
2. **tstar（T̂ 研究）はいまどこまで進み、meteo は何を待っているか**（`/home/futa/tstar`）
3. **着手可能な改善経路は何があり、どう優先順位づくか**（依存・dead-end・物差し別）
4. **今から着手する 1 タスクは何か、その根拠は何か**（ユーザー提示用）

### 3. 今後の AI 改善タスクの整理

手順 1〜2 で集めたオープン経路を、**物差し × 依存 × dead-end** の 3 軸で棚卸しする。

- **物差し別に分類**（`ai/OBJECTIVE.md`）:
  - **L1（厳密性）**: T̂ の順位保存率・q 厳密化。tstar 成果の受け入れ（C2 / 実分布ハイブリッド / LA1）が主。
  - **L2（self-play 不動点）**: パラメータの逸脱テスト（残対象＝deck15 速度ブロック・ギフト配り族の追検証など）。
  - **L3（家族外挑戦）**: 新ライン vs 現 champion（GRM 系の新形態、別アーキ）。
  - **OBJECTIVE §5**: 未解決の理論的論点（ギフト配り＝相互作用の本丸 / 終盤モード＝多人数性 / 均衡の非一意性）。
- **依存で分類**:
  - **tstar 依存（成果物待ち）**: 着手＝受け皿の整備と判定準備。tstar のジョブ状況に律速されるなら「待ち」と明示し、その間にできる非依存タスクへ。
  - **meteo 単独可**: `ai/SPEED-PLAN.md` の手法番号で。採用規律（事前宣言・完全未使用 seed・ゼロ損失証明）を満たせるか。
- **dead-end チェック**: **同一構成の単純再試行は除外**。dead-end 台帳は evolve-meteo-ai-handwritten スキル本文と `ai/CHANGELOG.md` が正。別角度・大規模化・新アーキは可（「その構成が効かなかっただけ」を区別する）。

整理結果は「経路名 / 物差し / 依存 / 状態（着手可・成果物待ち・要ユーザー・dead-end）/ 期待 EV（不確実でも明記）」の形にまとめる。

### 4. 今から着手するタスクの策定

整理した候補から **1 つ**を選び、ユーザー提示用に根拠を添える。

- **選定基準**（この順で判断）:
  1. **着手可能か** — tstar 成果物待ちなら、待ちが解消するまでの間に回せる meteo 単独タスクを優先（待ちを遊ばせない）。稼働中ジョブの完了が近いなら、その判定準備を先に。
  2. **物差しに紐づくか** — L1/L2/L3 または §5 のどれに貢献するか言えること。言えないなら候補から外す。
  3. **dead-end でないか** — 同一構成の再試行でないこと。
  4. **EV と不確実性** — 低 EV でも新角度なら可（強化は打ち止めにしない）。ただし EV と根拠を明示。
- **提示フォーマット**（ユーザーへ）:
  - 着手タスク 1 件（何を・どのファイル/受け皿で・どう測るか）
  - 物差し上の位置づけ（L1/L2/L3/§5 のどれ・なぜ）
  - 依存と前提（tstar 待ちか・必要な seed 帯・ゼロ損失か採用ゲートか）
  - 次点候補 1〜2 件（選ばなかった理由つき）
- **実行は渡す**: 選んだタスクが「1 改善仮説の実装〜採用判定」なら evolve-meteo-ai-handwritten スキルへ。tstar 成果物の受け取りなら受け皿整備＋fresh ゲートの段取りを提示。**このスキルは提案で止め、ユーザーの裁定を待つ**。

## 重要な原則

- **策定で止める**。実装・ベンチ・採用判定はこのスキルの責務外。議論段階で勝手に作業を始めない（`CLAUDE.md`）。
