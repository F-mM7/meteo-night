# tstar 依存事項・研究への要望

GRM の「計算時間を抑えつつ強さを保つ」改善のうち、**tstar リポジトリ（/home/futa/tstar、T̂ 研究）の結果に実施可否・導入度合いが左右されるもの**と、**tstar の研究方向への要望**の台帳。meteo-night 単独で進められる手法は `ai/SPEED-PLAN.md` に分離している。tstar 側セッションが読むことも想定する（tstar→meteo の引き継ぎは tstar/UPSTREAM.md、本書はその逆方向）。

現状の前提数値（2026-06-11、詳細は CHANGELOG）: 配信構成 GRM(V=20, P=P\*=0.5, K=6, budget=3000ms) は fresh 事前登録テスト 31.1%（CI 28.0-34.4、チャネル公平化込み）で旧既定 tempoChain に有意勝ち・1 手 max ~3.4s（オーバーシュート ~0.4s の主因は仕掛かり計算＋聖域 G ゲート＝q プローブ。h0 検証で確定）。無予算なら 37.0%（CI 32.5-41.8）。**残差 ~6pt が時間予算の劣化コスト＝tstar 成果のターゲット**。

## 1. C2（演算子フィット T̂）— 最優先・導入待ち

T̂ 本体（`estimateTHat` / `tHat`）の置き換え候補。tstar の i.i.d. 小型ベンチで MAE 0.49→0.058・相関 0.993・推論ミリ秒級・純 TS（重み JSON）。完成すれば精緻化も時間予算も実質不要になり「劣化」概念ごと消える＝残差 6.5pt の本命。

**導入可否を左右する点（tstar 側で要確認）**:
- 実サイズ（m=5, L=5, K=6, V=20）での学習・検証が成立するか（進行中と認識）
- i.i.d.→有限山札の分布ずれの扱い: (a) i.i.d. 近似のまま受容するか、(b) 山札色分布を特徴量に足して実遷移で再学習するか。**meteo 側の希望は、まず (a) で実サイズ精度を確認し、対戦勝率で足りなければ (b)**（(b) は backup 生成器のエンジン互換書き直しが必要で重い）

**tstar 側の進捗の観測（2026-06-14・meteo から git 確認。tstar の UPSTREAM 正式連携は未）**:
- **順位整合の世代選択を実装（tstar commit 2a685c7）**＝meteo が特定した「残る欠片＝h の順位品質」への直球。`fit --select rank` が、実サイズ合法な指標 `rankConsistency`（厳密 T* 不要・各候補の 1 段ベルマン backup を参照）で「素の h の argmin が backup の argmin と一致する世代」を選ぶ。**m=3 C2-h0 で実証**: 旧（残差最小選択）88.0%/76.0% → **rank 選択 gen18 で 90.0%/87.2%（P=1 +11.2pt 回復）**（成果物 `artifacts/c2-m3-h0-rank.json`）。「残差最小は h0 で初期世代を誤選択する罠」を是正。
- **ただし meteo 受け取りはまだ**: (i) **m=3 のみ**（meteo は m=5）。実サイズ rank 成果物は未完（`c2-real-prelim.state.json` は gen=1・稼働ジョブ無し＝停止中）。(ii) **依然 i.i.d. バックボーン**（rank は世代選択の改善で、i.i.d.→実分布のズレは別問題）。
- **meteo 側の実測との接続（REQUESTS で要望を訂正済み）**: 本日の uniformQ 対照（SPEED-PLAN 手法5 / CHANGELOG 2026-06-14）で**レート一様化だけで −4.7pt** を実測＝**順位品質（rank）と実分布レート（rate）は別軸で独立に効く**。**分業**: rate（実分布）は meteo の責務（hybrid で対応済み・順位 32.8→37.9%）、tstar は i.i.d. の順位品質に集中（貴 i.i.d. マンデートと整合）。
- **rank 再学習は低 EV と判明（2026-06-14 夜の精査）**: 既存実サイズ成果物 `c2-real-h0-pvgrid.json` は **selectedGen=24＝最終世代**で、m=3 では「最終世代≈rank 選択」なので rank で選び直すだけの再学習は期待値小（既に rank 相当を出荷済み）。**真のボトルネックは選択でなく実サイズ i.i.d. の順位品質そのもの**（小型 MLP は m=3 で argmax 88% なのに実サイズは rate 補正後ですら ~38% 止まり）＝容量/アーキ問題の可能性大。tstar も独立同結論（PLAN 2026-06-15「実サイズ rank は proxy フラットで gen1 誤選択・last が正・律速は値関数の局所順位の質」）。
- **GPU 大型関数族へ（tstar 側で着手済み・2026-06-15）＝meteo は成果物待ち**: ユーザー裁定で tstar が GPU 路線に着手（**RTX4080 は WSL2 からローカルに見えると判明**＝「別端末」記載は誤り・CUDA PyTorch 導入済み）。**容量（width）は両側テストで微増のみ**＝意思決定上は「width でなく depth が要るか」を GPU 深ネット（shallow/wide/deep A/B）で判定中: (a) meteo の容量切り分け（m=5 K2V4・hidden 24→128）＝rankAgree +2.35pt（69.19→71.54）、(b) tstar の width-96（実 config m5K6V20・hidden 24→96）＝holdoutResidual 0.16→0.14（race 強さ判定は別途）。**結論待ち**: 深ネットが baseline race 10.38 / proxy ~44% を超えれば天井破り＝meteo は hybrid×LA1 で即判定（受け皿 `leafFn`/`--h-swap la1`/`c2hInference.ts` 整備済み）。超えなければ「i.i.d. 順位品質は本質的に困難」が確定。**この実験は tstar セッションが主導中＝meteo は重複/競合編集を避けて待機**。

**tstar 側の進捗の取り込み（2026-06-12 朝の追記）**:
- **REQUESTS R1-R6 を消化し研究キューを再編**: 「h トラック」（R1-R4 への回答）を最優先キューに新設。①h0 を公式ベースラインとして tstar ベンチへ移植 ②R2 メトリクス（順位保存率・argmax 反転率）を m≤3 厳密 T* 基準でベンチ実装 ③**C2-h0**＝バックボーンを h0 に差し替えた残差学習が「プローブゼロ h 候補の本命」（素の C2 はバックボーン（greedy＋q プローブ）が R1 の硬条件に抵触するため。実行時 = h0 ＋置換不変特徴量＋小型 MLP 推論）。**meteo の degradeEstimate への最初の差し替え候補は C2-h0 になる見込み**。
- **実サイズ prelim の経過**: 初回は 7.3h 時点で V8 Map 上限クラッシュ（baseline の fireGCache 無上限＝**無上限メモ化バグ一族の 3 例目**。chain/meteo 側は対処済み、tstar 側も上限+テストで恒久修正）。分割実行（`--state`、中断→再開がビット一致）を実装し、走行中プロセスから CDP 読み取りで進捗を吸い出して再開状態化（gen1 42/400 盤面）。本日 ~15-17 時完了見込み。**prelim（v2 バックボーン）は速度不合格見込みと tstar 自身が予告**＝「実サイズで operator-fit が精度面で機能するか」の存在証明と位置づけ、速度は h トラック＋ D 節（q テーブル）で解く方針。
- 運用知見: 8 時間級ジョブは「午前開始 or 分割実行」（ユーザー指示）。走行中 node プロセスは SIGUSR1＋CDP で非破壊スタック/変数プローブ可能。

**tstar 側の進捗の取り込み（2026-06-11 夕）**:
- **V 汎化が m=3 で成立**（C2-6）: V∈{3,4,5}×P∈{0.5,0.8,1} の 9 組を単一重みでカバーし V 特化モデルと同水準（MAE 0.029-0.061・相関 ≥0.989、`tstar/artifacts/c2-m3-mlp-pvgrid.json`）。meteo の T̂ は V=20 固定運用なので必須ではないが、R5 で送った「実行時 V は 1..20 に閉じる」と整合し、終盤含む単一モデル供給の目処になる。実サイズへは「本番学習で vGrid を足すだけ」の位置づけ（tstar PLAN）。
- **実サイズ学習は worker 並列が実用不可と確定**: q メモがスレッド間共有できず総 CPU ~5.6 倍の冗長＋RSS 17.8GB（OOM 寸前）。縮小 serial の予備学習（P=0.8 単一・samples 400・gens 2 → `c2-real-prelim.json`）へ切替（本稿時点で成果物未着・ジョブ停止中）。**実サイズ C2 の到着時期は q 値前計算テーブル（下記 2 節）に律速される**＝2 節の優先度が学習側の事情でも上がった。
- 解析モデル路線（A2/A2b）の位置づけ確定: A2b-0 の解剖で「解析的プラン模型は F 回避スケジュール制約の壁に構造的に当たり続ける」と判明し、**A2b は単独 T̂ 候補から C2 の特徴量供給源へ格下げ**（tstar 側決定。本書 4 節に反映）。

**山札一様仕様についての方針合意（2026-06-11 ユーザー）**: 一様 i.i.d. は単なる近似でなく「山札を状態から外して状態数を潰し、浮いた計算量を探査・前計算・学習に回す」ための**構造的な設計選択**であり、meteo 側もこれを支持する。実測の裏付け: meteo の memo キー多様化（山札・捨札を含む）がメモリ・キャッシュ効率の主敵だったこと、強い偏り（色比率 33% 減）でも T̂ への影響は ~2 ターンで序中盤は小さいこと。導入時は「重い計算（q・needed）＝一様コア／安い最終段（レース式）＝実レート p_c 重み付け／終盤モードのみ実分布の厳密 q」のハイブリッドを既定方針とし、一様化の強さコストは meteo 側の対照実験（SPEED-PLAN.md 手法 5）で実測して線引きする。

**段階導入方針（2026-06-11 追記、同日 h0 実測で更新）**: C2 は一足飛びに T̂ 本体を置き換えず、**まず期限超過時の劣化先として導入する**（劣化先は決定の一部にしか効かないため精度バーが低く、fresh テストでの採否判定を小さく回せる）。meteo 側は劣化先を単一の差し替え点 `degradeEstimate`（`grmAI.ts`）に集約済み（実体は解析推定）。**探査ゼロの床 h0**（一様レート・発火形不足枚数レースの盤面のみ閉形式）を実体にする案は fresh テストで不通過（プール 23.63% < 基準 25%、CHANGELOG 2026-06-11）＝**「劣化先でも精度バーは現実に存在し、その軸は順位保存率」が定量的に裏付けられた**。C2 はまず劣化先 h 候補（h0 を順位保存率で上回ること）として接続し、実サイズで効果が確認できたら T̂ 本体（`estimateTHat` / `tHat`）の置き換えに進む。**h の品質軸は絶対 MAE より順位保存率**（同一決定内の候補順位の一致率。GRM は T̂ を比較にしか使わないため単調変換に不変＝順位が本質。要望 4 と同じ軸を劣化先 h にも適用、ベースラインは存置した `h0Turns`）。実行可能な要望の詳細は tstar/REQUESTS.md（R1-R6）。

**研究方向への要望**:
1. **P=0.5 を重点運用域に**: P 入力の単一モデル方針は維持しつつ、検証グリッドに P=0.5 を必ず含めてほしい（meteo の配信構成・強さ測定の既定が P=0.5＝**P\***（勝率最大化のフィッティング結果＝最適運用値の正式記号、REACHABILITY.md 記号表）。掃引実証: レース型相手には低 P が最適）
2. **実行時要件**: 1 手あたり T̂ 呼び出しは最大 ~50-100 回（取得チャネル比較＋配置候補）。1 呼び出し ≤1ms なら予算なしで 1 手 ≤0.1s 級になる
3. **受け渡し形式は現行どおり**: 純 TS 推論＋`artifacts/` の重み JSON（tfjs 不要）。meteo 側は `estimateTHat` の差し替え 1 点で接続できる形を維持する
4. **品質指標に「対戦勝率への波及」を意識した誤差軸を**: 絶対 MAE だけでなく、**候補間の順位保存率**（同一決定内の配置候補 ~50 個の argmax/順位が厳密 T̂ と一致する率）があると meteo 側の採用予測が立てやすい（GRM は T̂ を比較にしか使わないため、単調変換に不変＝順位が本質）

**meteo 側の受け入れゲート（固定）**: 差し替え後に完全未使用 seed 帯で事前登録 fresh テスト（基準: プール CI 下限 >25% かつ両ブロック点推定 >25%、vs tempoChain）＋レイテンシ実測。

## 2b. h ＋浅い先読み（LA1）— **新・有望路線（2026-06-12 tstar 実測）**

tstar の「強さ」主指標改訂（init 盤面・一様 i.i.d. レースベンチ・ナッシュ判定）で、**C2-h0-pvgrid ＋ LA1（候補評価を 1 段ベルマン backup に置換した先読み）が、現行解析系 v1 と同等のゴール速度（9.85 vs 9.82 ターン）を約 1/16 の計算量・予算内で達成**。生の h は方策として不成立（h0 単体 82 ターン）だが、**「探査ゼロの h ＋決定的な浅い展開」で化ける**＝meteo の到達目標アーキテクチャ②（決定的深さ打ち切り＋探査不要 h）と同型の構成が i.i.d. 世界で実証された。
- **meteo 実測（2026-06-12 夕）**: `leafFn` 注入点＋`--h-swap la1` を実装して対戦スクリーニング＝**30.00%（CI 23.44-37.50）**。生 C2-h0 の 21.9% から **+8.1pt**＝転移成立、ただし採用基準（CI 下限>25）には半歩届かず。**実分布対応 C2 × LA1 が閾値超えの本命**（受け皿存置）。
- 新成果物: `c2-real-h0-pvgrid.json`（V∈{5,10,15,20}×P グリッド・29.8µs・V 単調性 6.99<9.08<10.92<12.70）。
- 運用知見: 複数 V ジョブは Node 既定ヒープで OOM → ヒープ拡張必須（tstar 側ルール化済み）。GPU（RTX4080 別端末）が利用可能になったが現状 q の CPU DP が律速のため未使用。

## 4. A2b テンプレート型プラン（前計算）— **C2 の特徴量供給源へ格下げ（2026-06-11 tstar 決定）**

「G に届く盤面構造の雛形」を前計算し、実行時は不足ベクトル計算＋レース評価のみにする案。tstar の A2b-0 解剖（v3 楽観の主因＝**F 回避制約つき組み立てスケジュールの無視**。緩和の継ぎ足しでは理想に収束しない）により、単独の解析 T̂ 候補としては壁が確定。以後は C2 の特徴量（プラン不足ベクトル・q 値統計）の供給源として扱う。実サイズ空盤面の過大評価（v1 後の残差 Δ≈−4.6: T̂=18.9 vs MC 上界 ≤14.5）への本命は C2 へ一本化。

## 5. tstar ベンチ環境への要望（実サイズコストモデル）

v2（refineGate 拡大）が m=3 小型ベンチでは「×1.7」だったのに実サイズでは劣化率 4.4%→51% と破綻した教訓（UPSTREAM.md 連携済み欄に逆フィードバック済み）から:

- **速度評価は「T̂ 1 呼び出しの平均時間」だけでなく、q プローブ回数×実サイズの q 単価（分布、特に偽証明側の裾）で見積もれる形にしてほしい**。小型盤面の q は安すぎて、プローブ回数の増える改善のコストが見えない
- 可能なら実サイズの代表盤面セット（meteo 側で対局ログから供給可能）での wall-clock 計測を 1 軸追加
